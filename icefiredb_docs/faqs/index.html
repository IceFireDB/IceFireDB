                    Frequently asked questions #

                    Is it a Redis replacement? #

                    It speaks RESP and implements 110 commands with Redis semantics for most of them, so a Redis client connects without changes. But it is not a drop-in Redis: there is no WRONGTYPE, no SELECT, no transactions, no blocking commands, keys are limited to 1024 bytes, and three sorted-set commands do not replicate. Read Compatibility before migrating anything you care about.

                    Which commands are supported? #

                    110 data commands plus the RAFT/CLUSTER/MACHINE/BARRIER/AUTH system commands. The full list is in the command reference, one page per data type, with reply types and limits.

                    Why does INFO memory fail? #

                    Because INFO takes no arguments in this engine. Use INFO and parse the # Mem section out of the reply. See Observability.

                    Why is there no WRONGTYPE error? #

                    Because the storage model keeps one keyspace per data type, so a key name can hold a string, a hash and a list at once, and a wrong-type command operates on that type’s own view. There is also no TYPE command, so type safety is the application’s job. Pinned by compat_test.go.

                    Why did my HSCAN in Go/Python fail with a parse error? #

                    Because HSCAN/SSCAN/ZSCAN use the last field or member name as the cursor, not a number, and the typed client helpers coerce the cursor to int. Use the generic command API (Do, execute_command). SCAN’s own cursor is opaque base64 and is fine with Scan-style helpers. See Scan.

                    How do I configure it? #

                    Command-line flags only — there is no config file. --storage-backend, -a, -n, -d, -j, --auth, --tls-cert/--tls-key, --metrics, --pprof, the driver flags. The complete set with defaults is in Configuration.

                    Is --hot-cache-size a real flag? #

                    No. It is printed by -h but not registered, so passing it is an error and the cache capacity stays at the driver default (1024 MB). See flags that are printed but not wired.

                    Which storage backend should I use? #

                    goleveldb unless you have a reason. badger for heavier local writes, hybriddb for read-heavy working sets, oss when data must outlive the host, ipfs-synckv/crdt for multi-site P2P. The ipfs driver is not usable as a general backend today. See Storage backends.

                    How do I scale reads? #

                    Add nodes and run with --openreads so followers serve reads, or point a proxy at the followers. There is no sharding: every node stores the full dataset. See Clustering.

                    How do I back up and restore? #

                    RAFT SNAPSHOT NOW then copy RAFT SNAPSHOT FILE <id>, or copy a quiesced node directory. Restore with --restore <file> into a fresh data directory, then re-join the other nodes. Details and caveats in Operations.

                    Can I restore a badger backup into a goleveldb node? #

                    Yes for a snapshot (state.bin is a backend-independent key/value stream). No for a copied data directory — main.db/ is backend-specific and you must never change --storage-backend for an existing data directory.

                    Why did a follower return -MOVED 0 <addr>? #

                    Because without --openreads, followers refuse reads and redirect to the leader. Slot 0 is used for all keys; there is no sharding. With --try-errors the same reply becomes -TRY.

                    Where did my write go in a cluster? #

                    If it was ZINCRBY, ZREMRANGEBYRANK or ZREMRANGEBYSCORE, nowhere: those three are registered as read commands, so they mutate only the node you sent them to. Use ZADD with a computed score and ZREM.

                    Why can’t I use keys longer than 1024 bytes? #

                    Because ledis enforces 1 KiB keys, fields and set/zset members (values may be up to 1 GiB). It is a storage-layer limit, not a policy. Keep keys compact and hash long identifiers client-side.

                    Is it production ready? #

                    The engine ships as 1.0.0-rc.1. Local backends (goleveldb, badger, hybriddb), Raft replication, snapshots, TLS/auth and observability are exercised by CI (including crash-recovery, failover and partition tests). The decentralized drivers vary: ipfs-synckv is tested, crdt/ipfs-log are not unit-tested here, and ipfs cannot round-trip values. Own the risk accordingly.

                    Is there authentication, and is it per user? #

                    There is one shared token (--auth or ICEFIREDB_AUTH), required on every connection and shared by all nodes. No users, roles, or per-command permissions. Pair it with TLS. See Security.

                    Does it support transactions, pub/sub, streams or SQL? #

                    Not in this binary. MULTI/EXEC, pub/sub, streams and SQL are not implemented; pub/sub is a separate binary ( IceFireDB-PubSub) and SQL support lives in IceFireDB-SQLite/ SQLProxy.

                    What license is it under? #

                    Apache 2.0 for the engine; the PubSub component is MIT. See LICENSE in each directory.

                    Where do I report a bug? #

                    github.com/IceFireDB/IceFireDB/issues. A reproduction against make run plus the INFO output and the backend in use gets triaged fastest.
