                    与 Redis 的兼容性 #

                    IceFireDB 使用 RESP 协议，大多数命令的行为与 Redis 相同，但它不是 Redis：底层存储模型是 ledis，每种数据类型一个键空间，过期时间按整秒存储。本页列出客户端实际会注意到的差异，以及它们存在的原因。

                    标记为由测试锁定的行为由 compat_test.go（make test-compat）固定，除非有意更新，否则不会改变。

                    1. 没有 WRONGTYPE —— 每种数据类型一个键空间 #

                    Redis：一个键只持有一种类型的一个值；类型不符的命令会失败并返回 WRONGTYPE Operation against a key holding the wrong kind of value。

                    IceFireDB 为每种类型保留独立的键空间（string、hash、list、set、sorted set）。后果：

                    • 同一个键名可以同时持有字符串和哈希和列表。
                    • 类型不符的命令不会失败；它在该类型自己的（可能为空的）视图上执行。
                    • 根本没有 TYPE 命令，所以你无法查询某个键当前是什么类型。
                    SET k v          -> OK
HSET k f x       -> 1        # Redis: WRONGTYPE, here: fine
GET k            -> "v"
HGET k f         -> "x"

                    如果你的应用依赖 WRONGTYPE 来做类型安全，请在应用层自行保证（例如用 user:1:profile 与 user:1:fields 这样的键命名约定）。

                    由测试锁定 —— compat_test.go。

                    2. 过期时间按类型分开 #

                    没有针对单个键的统一 TTL。每种类型各有自己的：

                    类型过期命令PERSIST
                    字符串EXPIRE、EXPIREAT、TTL无（处理器未注册）
                    哈希HEXPIRE、HEXPIREAT、HTTL无（处理器未注册）
                    列表LEXPIRE、LEXPIREAT、LTTL无（处理器未注册）
                    集合SEXPIRE、SEXPIREAT、STTLSPERSIST（唯一一个）
                    有序集合无—

                    有序集合无法设置 TTL；请清掉它（ZCLEAR）再重建，或把过期信息保存在一个字符串键里。EXPIRE 只接受 KEY seconds —— 不支持 Redis 的 NX/XX/GT/LT 选项。

                    3. 过期时间精度为一秒 #

                    过期时间按整秒存储，因此 SET key value PX 500 会让键保留 1 秒，PX 1500 保留 2 秒（Redis 为 0.5 秒和 1.5 秒）。键绝不会比请求的时间更早过期，每个 *TTL 都报告整秒。

                    4. 空值在去中心化后端上会退化 #

                    HSET k f "" 之后 HGET k f：

                    • 在 goleveldb、badger、hybriddb 上：空 bulk string，与 Redis 一致；
                    • 在去中心化驱动上：nil ——“空”和“不存在”看起来一样。

                    GET 对字符串值遵循同样的规则。当“缺失”必须可区分时，不要存空字符串；存一个哨兵值，或利用哈希字段是否存在来判断。

                    5. 扫描游标不是整数 #

                    • SCAN 返回一个不透明的 base64 游标，携带五个子游标（每个键空间一个）。
                    • HSCAN/SSCAN/ZSCAN 返回最后一个字段名或成员名，因此名字恰好是 0 的字段会与结束标记冲突。
                    • 把游标当整数解析的客户端助手（go-redis 的类型化 HScan）会拒绝它；请使用通用命令接口。
                    • COUNT 上限为 10000，并且一页可能为空而游标仍然前进。

                    见 扫描。

                    6. 过期时间戳使用 Raft 时钟 #

                    每个过期时间都按 Raft 机器时钟（m.Now()）计算，从而保证每个副本一致；而存储层会用本地墙上时钟校验时间戳并报告 TTL。因此：

                    • 当 Raft 时钟落后于本地时间时，生命周期很短的键可能报告 TTL -1，尽管它仍有值；
                    • 比时钟偏差更短的过期时间会被拒绝，报 invalid expire value；
                    • 不同副本上的 TTL/HTTL/LTTL/STTL 可能相差各自的 apply 延迟。

                    实践中长 TTL 不受影响。不要在此基础上构建亚秒级语义。

                    7. 条件写看到的是本地过期检查 #

                    过期键按本地时钟异步回收，SET … NX/XX（以及 SETNX）通过同一个视图判断存在性。一个逻辑上已过期的键，在一个副本上可能仍然可见，在另一个副本上却不可见，因此两个副本对写入是否发生可能得出不同结论。

                    8. 列表重建不是事务性的 #

                    LINSERT 和 LREM 在存储层没有原语，因此处理器会重建列表（LRange → LClear → RPush，然后恢复 TTL）。重建发生在同一次 Raft apply 内，所以其他客户端看不到半成品列表，但中途后端失败会留下被截断的列表。两者都是 O(n)。

                    9. 三条有序集合命令不复制 #

                    ZINCRBY、ZREMRANGEBYRANK 和 ZREMRANGEBYSCORE 被注册为读命令，因此只修改接收请求的那个节点。在集群中这意味着不复制，也无法在 leader 切换后存活。修复前请用 ZADD 写入算好的分值，用 ZREM 删除成员。

                    10. 有上限的请求 #

                    有两个由客户端提供的数字被限制，以免单个请求产生无界的回复：

                    限制项取值违反时
                    任意 scan 的 COUNT10000夹到上限（仍只是提示）
                    `count作用于SRANDMEMBER`
                    SET … EX 会溢出 int64—返回错误，写入被拒绝

                    缺失的命令 #

                    人们常用、但本引擎没有注册的命令：

                    命令替代方案
                    SELECT无 —— 只有一个逻辑数据库
                    TYPE自行记录类型；键空间按类型划分
                    KEYSSCAN 0 MATCH pattern COUNT n（或 XSCAN）
                    DBSIZESCAN 后计数，或在应用中自行记录
                    MULTI/EXEC/WATCH没有事务；BARRIER 提供读己之写
                    BLPOP/BRPOP用 LPOP 轮询，或使用独立的队列系统
                    MONITOR未暴露
                    CONFIG GET/SET只能用命令行参数；修改后重启
                    PERSIST（字符串）、HPERSIST、LPERSIST再次 EXPIRE，或删除后重写
                    ZEXPIRE/ZTTL、ZPOPMIN/ZPOPMAXZCLEAR、ZRANGE/ZREM
