                    编解码层 #

                    这个引擎里的"编解码"指的是协议层结构与 ledis 写入的 KV 对之间的映射。它不是你可以选择的序列化格式——它由 ledis 固定，只能通过键限额、顺序、迁移这类副作用观察到。

                    哪些东西被编码 #

                    逻辑操作物理操作
                    SET k vPut(KVType + k, v)
                    HSET k f v字段为新增时：Put(HashType + k + f, v)、IncrBy(HSizeType + k, 1)
                    RPUSH k vPut(ListType + k + index, v)，更新 LMetaType + k（head、tail、count）
                    SADD k mPut(SetType + k + m, nil)、IncrBy(SSizeType + k, 1)
                    ZADD k score mPut(ZSetType + k + m, score)、Put(ZScoreType + k + score + m, nil)、大小计数器
                    EXPIRE k sPut(ExpTimeType + k, timestamp)、Put(ExpMetaType + k, …)

                    删除是逆操作：删一个哈希字段会移除一条 HashType 记录并递减大小计数器，而 HCLEAR 会遍历全部字段，并连计数器和过期记录一起移除。

                    类型字节为什么重要 #

                    因为类型是存储键的一部分，两种类型永远不会冲突，读时也不需要类型检查：GET k 只查 KVType + k，查不到就返回 nil，即使 HashType + k 下存在一个哈希。这就是没有 WRONGTYPE 的机制性原因——也是你无法向一个键询问它的类型的原因。

                    编码顺带给出的顺序保证 #

                    • 有序集合按编码后的分值记录排序：符号分隔符、大端分值、成员。范围查询是索引扫描，分值相同时按成员排序。
                    • 列表按 uint32 索引排序，另有一条 head/tail 元数据记录，因此 LPUSH 和 RPUSH 都是 O(1)，LINDEX 是直接查找——但 LINSERT/LREM 会重写整个范围。
                    • 集合与哈希没有内在顺序：遍历顺序就是后端的物理键顺序，所以 goleveldb 与 badger 的回复顺序不同，不能依赖。

                    值是不透明的 #

                    编解码层从不解释值。字符串值就是你发来的那些字节；哈希字段值也一样。压缩、加密和内容寻址属于驱动的职责（ipfs-synckv 做加密，ipfs 按 CID 寻址，badger 压缩块）。这就是为什么 --storage-backend 会改变持久性和隐私性，却从不改变命令语义。

                    迁移方面的影响 #

                    • 在这棵代码树里，编码在各版本之间保持稳定；改动它会破坏磁盘上的兼容性，这也是 COMMAND-AUDIT.md 里的存储行为台账被当作约定对待的原因。
                    • 快照不经过编码：writeSnapshot 流式输出原始的物理键/值对，所以恢复依赖目标二进制里存在相同的 ledis 编码。跨版本备份时要把这一点考虑进去：用 ledis 层与快照匹配的二进制来恢复。
