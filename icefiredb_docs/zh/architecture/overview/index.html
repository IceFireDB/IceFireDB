                    引擎概览 #

                    启动顺序 #

                    main() 做的工作很少而且固定，顺序很关键：

                    1. godotenv.Load() —— 如果存在 .env 就加载它。
                    2. confInit(&conf) —— 解析 flag，从环境变量解析 --auth，校验 TLS 配对与 --advertise， 把 --raft-backend 映射为 leveldb/bolt。
                    3. 注册 conf.DataDirReady 回调：当 Raft 层准备好节点目录后，它打开存储驱动（openStorage）并发布 ldb。命令处理器只有在这之后才可用，/readyz 就是为此存在的。
                    4. 后端指标注册到 INFO 采集器（hybriddb、ipfs、ipfs-synckv）。
                    5. 如已启用，启动 --pprof 与 --metrics 服务器——两者都是跑在 goroutine 里的普通 net/http 服务器。
                    6. 把 conf.Snapshot/Restore 接到 snapshot.go，把连接钩子接到客户端计数器，然后由 rafthub.Main(conf) 接管：恢复日志、在给了 -j 时加入集群、提供 RESP 服务。

                    请求路径 #

                    写命令（通过 AddWriteCommand 注册的 56 条命令）：

                    client → RESP parse → normalise (lowercase command name, args to strings)
       → leader check → append to Raft log → replicate → commit at quorum
       → apply on every node in log order → handler → ledis → driver

                    命令处理器是在应用阶段执行的，而不是在追加日志之前，这正是同样结果会出现在每个节点上的原因。因此，一个去读墙上时钟或 math/rand 的处理器必然产生分歧——它必须使用 m.Now()/m.Rand()，而这两个值本身通过内部 TICK 命令复制。

                    读命令（通过 AddReadCommand 注册的 54 条命令）：

                    client → RESP parse → (openreads? local : leader) → handler → ledis → driver

                    主节点在确认自己的已应用索引覆盖了该客户端此前的写入之后才提供读服务。从节点要么回复 -MOVED 0 <leader>，要么在开启 --openreads 时用自己已应用的数据提供服务。

                    系统命令（RAFT、CLUSTER、MACHINE、BARRIER）绕过数据空间，直接与 Raft 包装层通信。

                    组件及其位置 #

                    分层实现文件
                    RESP 服务器、流水线、认证、Rafttidwall/uhaha + tidwall/redconvendor/github.com/tidwall/uhaha
                    数据模型、按类型的键空间、TTLledisdb/ledisvendor/github.com/ledisdb/ledisdb/ledis
                    命令处理器本仓库strings.go、hashes.go、lists.go、set.go、sorted_sets.go、scan.go、servers.go
                    存储驱动本仓库 + ledisdriver/*、vendor/.../store/goleveldb
                    快照本仓库snapshot.go
                    可观测性本仓库 + Prometheus 客户端observability.go、server_info.go

                    进程模型 #

                    一个进程，每个连接一个 goroutine，一个 Raft 应用循环。没有按命令划分的线程池，也没有内部分区：一条慢命令会阻塞应用循环，所以 LINSERT/LREM 被记为 O(n) 的风险点，而 BLPOP 完全没有实现。

                    故障域 #

                    故障影响范围
                    写命令执行到一半时处理器返回错误该命令失败；此前已应用的写入保持已应用状态（无回滚）
                    列表重建过程中后端写入失败列表被截断（LINSERT/LREM）
                    进程崩溃未提交的日志条目丢失；已提交的条目从 store/ 恢复
                    节点磁盘损坏该节点从主节点的日志/快照重新加入；只要多数派还在，集群不受影响
                    多数派失效写入停止（-CLUSTERDOWN）；开启 --openreads 的读继续

                    这里刻意没有的东西 #

                    没有分片，没有 SQL 引擎，没有二级索引，没有脚本，没有发布/订阅，没有流，没有事务，没有向量检索。元素存储（IceFireDB-PubSub 以及各个 SQL 代理）是本仓库里另外的二进制，不是本引擎的功能。
