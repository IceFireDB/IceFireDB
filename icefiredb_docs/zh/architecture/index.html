                    架构

                    架构 #

                    这个二进制是如何一层一层拼起来的——以当前代码树里的实际形态为准，而不是当初的规划。

                    页面分层
                    概览启动顺序、请求路径、哪些东西在哪里运行
                    协议RESP 服务器、流水线、回复映射、集群重定向
                    网络Raft 传输、对等节点发现、P2P 驱动
                    存储ledis 数据模型、按类型的键空间、TTL、快照
                    编解码五种数据类型如何变成 KV 操作
                    RESP client ──► uhaha/redcon ──► Raft log ──► handlers ──► ledis ──► driver.IDB
                   │              (leader)      (110 cmds)   (types)   (8 drivers)
                   └── AUTH / PING / QUIT / RAFT / CLUSTER / MACHINE / BARRIER

                    阅读本站其余部分时，有两条边界值得记在心里：

                    • Raft 层负责顺序，不负责语义。 它决定一次写在何时生效；命令处理器决定它意味着什么。凡是必须在每个副本上完全相同的东西（随机数、时间）都由 Raft 层注入，命令处理器通过 m.Now() 与 m.Rand() 取用。
                    • 存储驱动负责持久性，不负责结构。 它只存不透明的键/值对。所有结构——哈希、列表、分值索引——都由驱动之上的 ledis 编码，这就是同一套数据模型既能在 LevelDB 上、也能在 IPFS 上成立的原因。
