                    存储层 #

                    命令处理器之下是 ledis：一个把五种 Redis 类型转换成单个 driver.IDB 上的键/值操作的数据模型。这也是同一组命令既能作用于本地 LevelDB 文件、又能作用于 IPFS 的原因。

                    按类型的键空间 #

                    ledis 不存"带类型的键"。它按类型存彼此独立的物理键，每个都带一个类型字节前缀：

                    类型前缀字节每个逻辑键对应的物理键
                    字符串KVType值本身
                    哈希HashType、HSizeType每个字段一条记录 + 一个大小计数器
                    列表ListType、LMetaType每个索引一条记录 + 一条元数据记录（head/tail/size）
                    集合SetType、SSizeType每个成员一条记录 + 一个大小计数器
                    有序集合ZSetType、ZSizeType、ZScoreType每个成员一条记录 + 大小计数器 + 每个（分值，成员）一条索引记录

                    过期时间也是独立记录（ExpMetaType、ExpTimeType），所以 TTL 属于设置它的那个类型，而不属于键名。

                    从客户端就能观察到的后果：

                    • 同一名称下可以并存两种类型（见 兼容性）。
                    • SCAN 必须遍历五个键空间；它的游标里带五个子游标。
                    • 删除哈希（HCLEAR）会移除很多物理键；DEL 只移除字符串那一条。

                    物理键编码 #

                    复合键采用长度前缀加分隔符，而不是哈希：

                    hash:   [index][HashType][uint16 keyLen][key][':'][field]
list:   [index][ListType][uint16 keyLen][key][uint32 index]
zset:   [index][ZScoreType][uint16 keyLen][key][sep][score][member]

                    有序集合的 sep 按分值符号取两个字节之一，因此索引的字节序与分值的数值序一致——这正是 ZRANGEBYSCORE 能做成范围扫描而不是全量排序的原因。成员记录按编码后的键排序，所以 SMEMBERS/HKEYS 的返回顺序是存储顺序，而不是插入顺序。

                    在这里而不是在处理器里执行的限额 #

                    限制项取值错误
                    键大小1024 字节，不可为空invalid key size
                    哈希字段大小1024 字节，不可为空invalid hash field size
                    集合成员大小1024 字节invalid set member size
                    有序集合成员大小1024 字节invalid zset member size
                    值大小1 GiBinvalid value size
                    过期时间戳早于当前时间—invalid expire value

                    这些来自 vendor/github.com/ledisdb/ledisdb/ledis/const.go；改它们就等于改 ledis。注意它们比 Redis 的 512 MB 值、几乎不限的键要严得多——1 KiB 的键预算才是大多数应用最先撞上的约束。

                    过期时间 #

                    • 过期时间以整秒存储，并按类型分别记录。
                    • 时间戳由命令处理器按 Raft 时钟算出，再由 ledis 对照本地时钟校验；<= now 的时间戳会被拒绝。
                    • 过期键是惰性/异步回收的，所以逻辑上已过期的键在另一个副本上仍可能被存在性检查看到。见 兼容性。
                    • TTL/HTTL/LTTL/STTL 用存储的时间戳减去本地时钟，“无过期"和"已过期"都返回 -1。

                    存储驱动与持久性 #

                    驱动的接口约定刻意做得很小（见 存储驱动）。在它之上：

                    • 写命令先经过 ledis，再走驱动的 Put/WriteBatch；--nosync 关掉的是 Raft 日志层里每次写入的落盘同步，不是驱动里的。
                    • 压实（compaction） 交给驱动（Compact()）；对 goleveldb/badger 就是普通的 LSM 压实，对 crdt/ipfs-log 则是空操作。
                    • 快照遍历驱动，在 gzip 容器里以 sds 格式流式输出键/值对，因此与具体驱动无关——见 运维。

                    这套设计为什么能成立 #

                    命令层从不假定具体存储。它向 ledis 要操作（HSet、LPush、ZRangeByScore 等），由 ledis 把它们映射成带前缀的键操作。让这个引擎成为数据库的一切——结构、顺序、过期——都活在这层映射里，所以新的存储驱动只需要是一个正确的有序 KV 存储。

                    代价落在边角上：没有跨类型原子性、O(n) 的列表重建、基于名字的扫描游标，以及 1024 字节的键预算。这些都被当作局限记录下来，而不是糊过去。
