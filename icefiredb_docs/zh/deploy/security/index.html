                    安全 #

                    引擎有三个与安全相关的面：RESP 监听器、Raft 传输，以及可选的管理 HTTP 服务。它们共用一个凭据和一份 证书。

                    传输加密（TLS） #

                    ./bin/IceFireDB --tls-cert ./server.crt --tls-key ./server.key -a 0.0.0.0:11001 -d /var/lib/icefiredb
                    • 两个参数必须一起给出——只给其中一个会在启动时报错。
                    • TLS 作用于唯一的监听 socket。RESP 客户端和 Raft 传输都到达它上面，服务端通过嗅探首字节来分辨 哪个是哪个。没有第二个端口。
                    • 因此 --advertise 的值必须是节点和客户端使用的 TLS 地址。
                    • 客户端也必须走 TLS：redis-cli --tls --cacert ./ca.crt -h host -p 11001，或等效的客户端选项 （go-redis：TLSConfig；Python redis.Redis(ssl=True)；Node tls: {}）。
                    • 证书需要为客户端使用的名字提供一个 DNS: SAN；服务端会把第一个 DNS SAN 复制进用于出站连接的 tls.Config.ServerName。
                    • 没有客户端证书。 tls.Config 只用 Certificates 构建，所以既没有 mTLS，也没有客户端身份。 节点之间用共享 token 认证，而不是证书。

                    集群授权 #

                    export ICEFIREDB_AUTH='openssl rand -hex 32'    # preferred: not visible in the process list
./bin/IceFireDB -a 0.0.0.0:11001 -d /var/lib/icefiredb
# or
./bin/IceFireDB --auth '<token>' -a 0.0.0.0:11001 -d /var/lib/icefiredb

                    它做什么：

                    • 客户端必须在任何其他命令之前先发送 AUTH <token>。token 错误会回复 -unauthorized。
                    • 所以连接上的第一条命令必须是 AUTH。所有主流客户端库在你配置密码时都会自动这么做 （redis-cli -a、go-redis Password、Python password=、Node password:）；自己手写的客户端 如果先发命令，在当前构建里不会得到干净的错误回复（见 已知缺口）。
                    • 节点在加入集群、读取日志索引和转移领导权时用同一个 token 相互认证。每个节点必须共享这个 token，在任一节点上改动它都会破坏集群。
                    • 它是单一的共享密钥，没有用户、角色或按命令权限的概念。这个引擎目前没有 ACL 子系统：谁持有 token，谁就能写、清空（FLUSHALL）、更改集群成员（RAFT SERVER ADD|REMOVE）以及关闭进程 （SHUTDOWN）。

                    它不做什么：

                    • 没有限流、没有锁定、没有 token 轮转、没有按键授权。
                    • 没有记录谁执行了什么的审计日志（MONITOR 式的观察者是内部的，不暴露 raft/auth/cluster 命令）。
                    • 它不加密流量——在你不拥有的任何网络上都要配合 --tls-cert/--tls-key 使用。

                    管理 HTTP 服务 #

                    端点组参数默认绑定认证
                    /healthz、/readyz、/metrics--metrics127.0.0.1:11002无
                    pprof（/debug/pprof/*）--pprof127.0.0.1:26063无

                    两者默认关闭，并且正因为不带认证而绑定到回环地址。/metrics 和 /debug/pprof 会泄漏运维细节， 在高负载下还会阻塞或分配内存；把它们放在私有网卡、sidecar，或强制身份的 反向代理 之后。

                    推荐的基线 #

                    ICEFIREDB_AUTH="$(cat /run/secrets/icefiredb-auth)" \
./bin/IceFireDB \
  --tls-cert /etc/icefiredb/tls/server.crt --tls-key /etc/icefiredb/tls/server.key \
  -a 0.0.0.0:11001 --advertise db1.internal:11001 \
  -d /var/lib/icefiredb \
  --metrics --metrics-addr 127.0.0.1:11002 \
  --storage-backend goleveldb
                    1. 除非只能通过私有网络访问，否则绝不要在无 TLS 的情况下暴露 RESP 端口。
                    2. 把 token 放在 ICEFIREDB_AUTH 或 .env 文件里（二进制启动时会加载 godotenv），绝不要放在 shell 历史里，也不要放在全局可读的 unit 文件里。
                    3. 把 --metrics/--pprof 留在回环地址上；从同一台主机抓取它们。
                    4. 把 FLUSHALL、RAFT SERVER REMOVE 和 SHUTDOWN 当作等价于 root 的操作，因为它们确实是。
                    5. 用拥有数据目录的非特权用户运行进程；-d 只需要对该目录树有写权限。

                    工具链与已知漏洞 #

                    依赖集用两种方式检查：GitHub Dependabot 告警（任何涉及 go.mod 中模块的公告），以及 govulncheck . （只算真正编译进去的代码里可达的漏洞）。后者才描述风险。当前被接受的有两条，都在 libp2p 路径上：

                    编号模块为什么没修何时可达
                    GO-2026-4479github.com/pion/dtls/v2@v2.2.12v2 没有修复版本；kubo、boxo、ipfs-lite 与 IceFireDB 的几个 fork 仍依赖它libp2p 的 WebRTC 传输，即只在去中心化后端（crdt、ipfs、ipfs-log、ipfs-synckv）下可达
                    GO-2024-3218github.com/libp2p/go-libp2p-kad-dht@v0.38.0修复需要 kad-dht >= 0.40，其 dht.New/dualdht.New 签名变更会打断同一组上游依赖同上，libp2p/DHT 路径

                    实际含义：GA 后端（goleveldb、hybriddb）运行时根本不进那段代码；缓解手段是网络暴露面 —— 把去中心化 后端的 libp2p 端口挡在不可信网络之外。完整记录以及每条在什么条件下可以关掉，写在引擎仓库的 SECURITY.md 里；kubo、ipfs-lite 与 IceFireDB 各 fork 协调升级之后用 govulncheck . 复查。

                    已知缺口 #

                    • 没有按用户的 ACL（作为未来工作跟踪，本代码树中未实现）。
                    • 没有 token 轮转协议：轮转 token 意味着协调一致的重新启动。
                    • 对已经持有 token 的恶意节点没有防护——集群成员资格是首次使用即信任加上共享密钥。
                    • 在 AUTH 之前（或 AUTH 失败之后）发送的命令，在当前构建里不会得到错误回复：对于未认证的 命令，分发器把响应槽留空。先发 AUTH，就像所有客户端库那样，并且把 token 当作连接时的凭据，而不 是可以在连接中途去提示输入的东西。
