                    集群 #

                    集群是一组共享同一份 Raft 日志的节点。每条写命令都会追加到该日志，并由每个节点重放，因此所有节点 收敛到同一状态；读命令由收到它的那个节点在本地应答。

                    引导与加入 #

                    第一个节点不需要额外 flag：-j 为空即表示「开启一个新集群」。之后每个节点用 -j <leader-or-any-node-address> 加入：

                    ./bin/IceFireDB -n 1 -a 127.0.0.1:11001 -d ./data
./bin/IceFireDB -n 2 -a 127.0.0.1:11002 -d ./data -j 127.0.0.1:11001
./bin/IceFireDB -n 3 -a 127.0.0.1:11003 -d ./data -j 127.0.0.1:11001

                    加入时，节点用 AUTH（若设置了 --auth/ICEFIREDB_AUTH）和 TLS（若配置了证书）连接该地址，请求 当前的集群状态，把自己加进去，然后从日志追赶。在同一数据目录上重启的节点不需要再次 -j —— 它会从 已持久化的 Raft 状态重新加入。

                    当绑定地址不是对等节点应当拨号的那个地址时（容器、NAT、多网卡），请使用 --advertise：

                    ./bin/IceFireDB -n 2 -a 0.0.0.0:11001 --advertise 10.0.0.12:11001 -d /var/lib/icefiredb -j 10.0.0.11:11001

                    通告地址就是客户端在 -MOVED 重定向中收到的地址，也是其他节点写入 Raft 配置的地址，因此它必须 对对等节点可达，也对客户端可达。

                    一致性模型 #

                    操作在哪里执行保证
                    写命令（SET、HSET、RPUSH、…）只在主节点执行，经 Raft 日志在每个节点上按相同顺序应用；写入在多数派提交后才被确认
                    读命令，未启用 --openreads收到它的节点；在从节点上会被拒绝从节点返回 -MOVED 0 <leader>；客户端向主节点重试
                    读命令，启用 --openreads任意节点可能返回陈旧数据（本地日志已应用到的状态）
                    RAFT …、CLUSTER …、MACHINE、BARRIER收到它的节点管理操作，不复制

                    启用 --try-errors 后，重定向错误变成 -TRY <leader>，且 CLUSTER 命令被禁用；这是为那些需要 区分「去别处重试」与「集群把我重定向了」的客户端准备的。

                    只有在节点认为日志已基本加载完成后，才会提供从节点读；在那之前，它按非主节点身份应答。

                    拓扑管理 #

                    成员变更通过 Raft 配置进行，而不是配置文件。支持的两条路径是等价的 —— 第一条正是 -j 内部所做的 事：

                    # path 1 — let the node add itself
./bin/IceFireDB -n 4 -a 127.0.0.1:11004 -d ./data -j 127.0.0.1:11001

# path 2 — add it from an existing node, then start it
redis-cli -p 11001 RAFT SERVER ADD 4 127.0.0.1:11004
redis-cli -p 11001 RAFT SERVER LIST
redis-cli -p 11001 RAFT SERVER REMOVE 4

                    需要留意的规则：

                    • 替换节点时先添加、再移除。 移除成员会缩小多数派的要求，而两节点集群完全没有冗余 —— 在替换 过程中，存活的多数派必须仍然足够选出主节点。
                    • 绝不要把同一个节点 ID 配上不同的数据目录。 该 ID 就是 Raft 服务器 ID； <dir>/IceFireDB/<id>/ 中的状态属于它。
                    • 必须有大多数节点存活才能选出主节点。 失去多数派不会破坏数据，但写入会停止，需要主节点身份的 读操作会以 -CLUSTERDOWN 失败。
                    • 完整的命令通道列表见 系统命令。

                    快照 #

                    Raft 会对状态机做快照，以便日志可以被截断。每个快照都写入 <data-dir>/IceFireDB/<node-id>/snapshots/<snapshot-id>/state.bin。这个文件是 gzip 压缩流：先是 32 字节头（SNAP0001 + 机器启动时间、时间戳、随机数种子），随后是 snapshot.go 中 writeSnapshot 以 sds 帧格式写出的全部键/值对 —— 每条一个键/值对，与具体存储驱动无关。

                    redis-cli -p 11001 RAFT SNAPSHOT NOW        # take one immediately
redis-cli -p 11001 RAFT SNAPSHOT LIST       # id, timestamp and size per snapshot
redis-cli -p 11001 RAFT SNAPSHOT FILE <id>  # path on the server that produced it

                    快照文件是备份与灾难恢复的单位；见 运维。

                    故障行为 #

                    故障影响
                    一个从节点宕机（3 节点集群）对写入和主节点稳定性没有影响
                    主节点宕机从节点选出新的主节点；在途未提交的写入可能丢失；客户端在重新发现主节点之前会看到 -MOVED/-TRY
                    少数派分区少数派一侧无法选举，其写入以 -CLUSTERDOWN 失败；多数派继续提供服务
                    用同一数据目录重启的节点从持久化状态重新加入，从日志或快照追赶
                    使用全新数据目录、但沿用已有节点 ID 启动的节点被集群以 ID 冲突拒绝 —— 清空该目录或换用新的 ID

                    在启用 --openreads 的从节点上，读在主节点选举期间仍然可用，代价是提供的状态可能落后。

                    集群不做的事 #

                    • 没有分片：每个节点持有全量数据集。对能识别 redis-cluster 的客户端，CLUSTER SLOTS 会在主节点上 报告完整的 0-16383 区间，但并不存在键的分布。
                    • 除 Raft 之外没有 read-repair 或 anti-entropy：已经追上的节点会通过日志保持同步。
                    • ZINCRBY、ZREMRANGEBYRANK 与 ZREMRANGEBYSCORE 被注册为读命令，因此不会复制。见 兼容性。
