                    存储驱动 #

                    --storage-backend <name> 选择位于 ledis 数据模型之下的驱动。命令层是针对 store.driver.IDB 编写的，所以同一套命令在每个后端上都能跑——变的是字节存放在哪里、由谁复制它们，以及这个驱动能信到 什么程度。

                    type IDB interface {
    Close() error
    Get(key []byte) ([]byte, error)
    Put(key []byte, value []byte) error
    Delete(key []byte) error
    SyncPut(key []byte, value []byte) error
    SyncDelete(key []byte) error
    NewIterator() IIterator
    NewWriteBatch() IWriteBatch
    NewSnapshot() (ISnapshot, error)
    Compact() error
    GetStorageEngine() interface{}
}

                    每个后端是什么 #

                    --storage-backend数据在哪复制方式外部依赖
                    goleveldb （默认）本地 LevelDB（纯 Go）仅 Raft—
                    badger本地 BadgerDB v4，ZSTD 压缩仅 Raft—
                    hybriddb本地 LevelDB + Ristretto 热缓存，按驱动暴露指标仅 Raft—
                    ossS3 兼容对象存储，本地 LevelDB 索引 + Ristretto 缓存仅 RaftS3/MinIO 端点
                    ipfs本地 LevelDB，其值按 CID 从 IPFS 取回仅 RaftIPFS API（不是网关）
                    ipfs-synckvIPFS 作为真值来源 + 本地镜像 + 版本元数据，可选 AES-256IPFS/ipfs-log P2PIPFS API + P2P
                    crdt本地 Badger + 基于 libp2p pubsub 的 icefiredb-crdt-kvP2P CRDTlibp2p 对等节点
                    ipfs-log基于 IPFS pubsub 的只追加 icefiredb-ipfs-log 存储P2P 日志IPFS + P2P

                    leveldb（cgo 驱动）和 orbitdb 没有被编译进二进制：前者从未被 import，后者在 main.go/flags.go 里被注释掉。传入这两个名字中的任何一个都会在启动时报 “unknown driver”。

                    如何选择 #

                    • 默认 / 大多数负载 — goleveldb。纯 Go、无 cgo、内存可预测、无外部服务。
                    • 写密集的本地负载 — badger。注意该驱动打开时用的是很大的固定默认值（1 GB memtable、1 GB block cache、100 个 goroutine/compactor），所以主机规格要按此配置。
                    • 能装进内存的读密集工作集 — hybriddb。热层吸收读请求，该驱动会把 read_operations、 write_operations、bytes_read、errors …… 注册进 INFO。
                    • 必须比主机活得更久的数据 — oss，配合 --oss-endpoint、--oss-ak、--oss-sk。每次写都 进入对象存储，本地 LevelDB 索引让它仍然可寻址；本地磁盘要留着，因为索引在上面。
                    • 多站点 / 去中心化 — ipfs-synckv 或 crdt。两者都通过 libp2p pubsub 复制，用 --servicename、--nettopic、--datatopic 配置（三者必须在所有节点上一致）。
                    • 目前不能当通用后端用 — ipfs。它的写路径把原始值存在本地，而读路径把存下来的字节当作 IPFS CID 去 cat，所以通过引擎写入的值取不回来。想要 IPFS 持久化就用 ipfs-synckv。

                    各后端的配置 #

                    后端参数默认值
                    ipfs、ipfs-synckv--ipfs-endpointhttp://localhost:5001（API 端口，不是 8080 网关）
                    ipfs-synckv--ipfs-synckv-key空 → 不加密；32 字节的密钥启用 AES-256
                    ipfs-log--ipfs-log-dbname，或环境变量 IPFS_LOG_DBNAMEifdb-event-kv-ipfs-log
                    oss--oss-endpoint、--oss-ak、--oss-skhttp://localhost:9000 + 占位凭据
                    crdt、ipfs-log--servicename、--nettopic、--datatopicicefiredb、icefiredb-net、icefiredb-data

                    oss、ipfs 和 ipfs-synckv 的热缓存容量不能从命令行配置：它是驱动里的常量 1024 MB。见 配置。

                    你能得到和得不到的保证 #

                    你能得到

                    • 每个后端上相同的命令语义，包括按类型分离的键空间和按类型分离的过期时间。
                    • 与后端无关的 Raft 快照/恢复：writeSnapshot 遍历驱动的快照，在 gzip 文件里以 sds 格式流式写出键/值对， 所以在 badger 上做的备份可以恢复到全新的 goleveldb 节点（见 运维）。
                    • hybriddb、ipfs、ipfs-synckv、oss 在 INFO 中提供后端指标。

                    你得不到

                    • 没有跨后端的磁盘格式兼容性。 不要为已有的数据目录更换 --storage-backend；这些格式互不相关。
                    • 去中心化驱动上没有"空值"区分。 它们把"缺失"和"空"合并，所以空字符串读回来是 nil 回复。这一点 在 兼容性中已固定。
                    • 没有驱动级的重试或修复。 失败的写会作为命令错误暴露出来；在 P2P 驱动上，暂时不可达的对等节点 表现为数据缺失，直到日志追上。
