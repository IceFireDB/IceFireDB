                    运维 #

                    单节点或 Raft 集群的备份、恢复、升级与故障恢复。所有东西的单位是节点目录： <data-dir>/IceFireDB/<node-id>/。

                    磁盘上有什么 #

                    路径内容备份方式
                    main.db/所选驱动格式的 ledis 存储复制该目录
                    store/Raft 日志 + 稳定存储（leveldb 或 bolt）复制该目录
                    snapshots/<id>/state.binRaft 状态机快照：gzip 头（start/ts/seed）+ sds 键/值流RAFT SNAPSHOT，或复制该目录

                    state.bin 与后端无关：writeSnapshot 遍历驱动的快照，把 key, value 对写进一个 gzip 流。这就是为什么在 badger 节点上做的快照可以恢复到 goleveldb 节点，而 main.db/ 目录本身永远不行。请把这个文件当作不透明的： 整体复制（或用 RAFT SNAPSHOT READ 按窗口读取），再用 --restore 交回去 —— 不要解压或修改它。

                    备份 #

                    方案 A——快照状态机（推荐，可移植）

                    redis-cli -p 11001 RAFT SNAPSHOT NOW            # returns the new snapshot id
redis-cli -p 11001 RAFT SNAPSHOT LIST           # ids and sizes
redis-cli -p 11001 RAFT SNAPSHOT FILE <id>      # absolute path on the server
# copy that file off the host:
scp db1:/var/lib/icefiredb/IceFireDB/1/snapshots/<id>/state.bin ./backup-$(date +%F).sds

                    对于很大或带宽受限的快照，按窗口读它，而不是复制文件：

                    redis-cli -p 11001 --raw RAFT SNAPSHOT READ <id> RANGE 0 1048576 > part-000
redis-cli -p 11001 --raw RAFT SNAPSHOT READ <id> RANGE 1048576 1048576 > part-001

                    方案 B——复制节点目录（对整个集群最快）

                    停止写入，或者挑一个从节点让它稳定下来，然后复制整个 <data-dir>/IceFireDB/<node-id>/ 目录树。 在写负载下复制主节点，得到的目录在某个较近的日志索引处是内部一致的，但"某个索引"不是你控制的点 ——要一份能推理的备份，就用方案 A，或者让节点静默。

                    恢复 #

                    --restore 从快照文件引导一个全新的单节点集群：

                    mkdir -p /var/lib/icefiredb-restore
./bin/IceFireDB -n 1 -a 127.0.0.1:11001 -d /var/lib/icefiredb-restore \
  --restore ./backup-2026-11-08.sds

                    规则，全部由 Raft 层强制执行：

                    • 如果 <data-dir>/IceFireDB/<node-id>/ 已经存在，--restore 会被忽略。请用一个新的目录。
                    • 它不能与 -j 组合使用；被恢复的节点就是新的单节点集群。
                    • 其他每个节点都必须清空并用 -j <restored-node-addr> 重新加入——它们的日志指向一个已经不存在的 集群历史。
                    • 恢复时每 1000 对写一批，所以内存是有界的，大快照不需要整个塞进内存。

                    滚动升级 #

                    一次一个节点，从节点先升级，主节点最后：

                    1. 检查健康 — CLUSTER INFO 报告 cluster_state:ok，RAFT SERVER LIST 列出每个成员，所有 节点的 /readyz 都是 200。
                    2. 升级一个从节点。 停掉它，替换二进制，用相同的 -n、-a 和 -d 启动它。它从持久化的 Raft 状态重新加入，并从日志或快照追上。
                    3. 等待 /readyz 返回 200 且它的 RAFT INFO 索引追上，再去动下一个节点。
                    4. 最后升级主节点。 停掉它；一个从节点被选出；启动升级后的二进制；它作为从节点重新加入。

                    绝不要一次干掉多数派：没有多数派时，写入会以 -CLUSTERDOWN 失败，直到能再次选出主节点。

                    对已有数据目录的兼容规则：

                    要做不要做
                    保持 -n、-a 和 -d 不变更改节点 ID，或把目录移到另一个节点
                    在每个节点上保持 --auth/ICEFIREDB_AUTH 一致逐节点轮转 token
                    保持 --storage-backend 原样在已有的 main.db 上切换存储驱动
                    保持 --raft-backend 原样在已有的 store/ 下切换 Raft 日志格式

                    灾难恢复 #

                    丢失一个节点 — 给它一个新的目录（或清掉旧目录），然后把它加入：

                    rm -rf /var/lib/icefiredb/IceFireDB/3
./bin/IceFireDB -n 3 -a 10.0.0.13:11001 --advertise 10.0.0.13:11001 -d /var/lib/icefiredb -j 10.0.0.11:11001

                    如果旧的成员记录仍然存在而该节点无法重新加入，先从健康成员上删掉它：RAFT SERVER REMOVE 3，然后 用 -j 启动该节点。

                    丢失多数派 — 写入已停，但数据仍然存在于存活的节点上。把最新的快照恢复进一个全新的单节点集群 （--restore，见上），然后用 RAFT SERVER ADD 或 -j 把其他节点加回来。那个快照之后写入的数据会 丢失；这是唯一不需要多数派的恢复方式。

                    存储损坏 — main.db/ 可以按驱动修复（例如 GoLevelDB/Badger 的恢复工具），但受支持的路径是： 移除该节点，从最新的快照恢复，重新加入。

                    例行检查 #

                    # is the process serving?
curl -fsS http://127.0.0.1:11002/healthz
curl -fsS http://127.0.0.1:11002/readyz

# is the cluster healthy?
redis-cli -p 11001 CLUSTER INFO
redis-cli -p 11001 RAFT SERVER LIST

# is it roughly in sync? (compare a sample on two nodes)
redis-cli -p 11001 --scan --pattern 'sample:*' | head -50 | xargs -n1 redis-cli -p 11001 GET

                    容量说明 #

                    • 每个节点都存完整数据集；没有分片。磁盘规划是按节点算，不是按集群算。
                    • --nosync 用持久性换写吞吐；绝不要用在断电后还打算从它恢复的节点上。
                    • badger 以 1 GB memtable 和 1 GB block cache 的默认值打开；要为它们留出预算。
                    • Raft 快照会在 snapshots/ 下累积；Raft 层会剪掉旧的，但在一个从不做快照的节点上，日志会一直增长 到下一次快照——为这部分磁盘占用做规划。
