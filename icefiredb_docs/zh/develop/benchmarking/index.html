                    基准测试 #

                    本页讲的是怎么测量这个引擎。它刻意不含任何性能数字：一个数字如果没带上产生它的 commit、硬件、存储驱动和 flag，就只是噪声。

                    能用的压测工具 #

                    redis-benchmark 和 memtier_benchmark 都能用，因为线上协议就是 RESP。

                    # baseline: one connection per request, no pipeline
redis-benchmark -h 127.0.0.1 -p 11001 -t set,get -n 200000 -c 50

# pipelined
redis-benchmark -h 127.0.0.1 -p 11001 -t set,get -n 1000000 -c 50 -P 16

# mixed, with memtier
memtier_benchmark -s 127.0.0.1 -p 11001 --protocol=redis \
  --clients=50 --threads=4 --ratio=1:1 --test-time=120 --key-pattern=S:S

                    它们不会覆盖到的部分：

                    未覆盖原因
                    SCAN/XSCAN 分页没有内置负载；用脚本驱动
                    集群重定向压测直接打主节点，否则错误计数里会出现 -MOVED
                    TTL 过期压力给 SET 负载加上 EX，然后观察 INFO Store
                    Raft 应用延迟写命令在多数派确认后才应答；增加节点才能看出差值

                    必须保持恒定的项 #

                    任何结果都要连同下面这些一起记录，否则数字不可比较：

                    1. Commit —— git rev-parse HEAD，以及 -h 输出的 BuildVersion。
                    2. 存储驱动 —— --storage-backend，对 badger/hybriddb 还要记宿主内存（这两个驱动默认以 1 GB memtable / 大缓存打开）。
                    3. 持久性 —— --nosync 开或关。这通常是写入侧影响最大的单一因素。
                    4. 集群规模与读模式 —— 1 节点 vs 3 节点；--openreads vs 只走主节点。
                    5. 客户端侧 —— 连接数、流水线深度、值大小，以及客户端是否在同一台机器上（回环会把网络开销藏起来）。

                    值得跑的负载 #

                    负载命令形态它能告诉你什么
                    单点写SET key <256B>Raft + 存储的写入路径
                    单点读GET key缓存 + 存储的读取路径
                    计数器INCR hits应用循环内部的读-改-写
                    哈希写HSET k f v多记录编码的成本
                    列表 push/popRPUSH q v / LPOP q索引编码、元数据更新
                    ZSet 写ZADD board <score> m每个成员两条索引
                    范围读ZRANGE board 0 100 WITHSCORES索引扫描效率
                    大值SET k <64KiB>内存分配、回复体积、GC 压力

                    压测时同时观察服务端 #

                    watch -n1 'redis-cli -p 11001 INFO | sed -n "/# Store/,/# Mem/p"'
curl -s http://127.0.0.1:11002/metrics | grep icefiredb_connected_clients

                    INFO 给出进程级计数器（get、get_missing、put、batch_commit 及其总耗时），通常比压测工具自己的分位数更有信息量：吞吐平稳而 batch_commit_total_time 持续上升，说明瓶颈在存储设备而不是引擎。

                    反模式 #

                    • 在没开 --openreads 的情况下压测从节点。 每次读都会变成一次重定向，测出来的是客户端重试循环。
                    • 把 --nosync 的运行和持久化运行放在一起比较。 两者保证不同；要么都报，要么都不报。
                    • 在吞吐测试里用 LINSERT/LREM。 它们会重建整个列表；测到的是 O(n) 重写，不是列表性能。
                    • 无视应用循环。 吞吐受限于单个应用 goroutine，所以客户端线程加到某个点就不再有用；去找那个点，而不是假设它不存在。
                    • 引用本页的数字。 本页故意没有任何数字。
